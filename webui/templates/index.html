Pre-flight readiness check

Static checks (config, paths, rules, ECS, mapping) always run. Live checks (Kafka / Redis / TCP) need those services reachable from this machine.

1 · Capacity — what can this machine parse?

Runs every rule against its sample corpus on one core: EPS, parse latency (avg/p50/p95/p99) and live utilization vs the running engine. CPU-heavy while it runs (roughly 15–60 s).

2 · Live lag — is the pipeline real-time right now?

Reads the tail of each module's output file: lag = event.ingested − @timestamp. Steady sub-second lag = healthy; negative or hours-sized lag = a source host's clock / timezone label is wrong, not the engine.

3 · History — how did it perform last week / during a spike?

Elasticsearch reconstructs the lag/EPS timeline from the stored events — e.g. how a mass onboarding behaved, hour by hour. Uses the same ELK sign-in this console already has, so the password can stay empty. Large patterns can take a minute.

Using the console

  1. Test Log — paste log lines or upload a file, pick a parser (or AUTO to let the engine find the right one), and Run. You get the parsed ECS JSON plus a parsed / no-match summary.
  2. Rules — click a rule to view/edit its YAML. Use a template to start a new parser, Check ECS fields to validate field names, then Save.
  3. Config — edit config.yaml and Validate it (same checks as the CLI validator) before going live.
  4. IP Map — like GeoIP, but for YOUR network: describe which internal range is which building/room/lab, and matching events are enriched with those fields. + Add entry opens a form (range → name → fields, each field ECS-checked as you type); edit/duplicate/delete entries in the table, Save, then Try an IP to see the result. The running engine picks up saves within ~10 s; a Raw YAML mode exists for hand-editing.
  5. ECS Helper — look up the correct ECS field for any concept, or autocorrect a wrong name.
  6. Preflight — when you are ready to connect Kafka/Redis, run the live readiness check.
  7. Benchmark — measure what this machine can parse (EPS + latency + utilization %), check whether the live pipeline is real-time, or reconstruct how it performed during a past traffic spike.
